# Capture Source Protocol

Status: Formal design contract, implementation pending  
Protocol identifier: `capture-source/v1`  
Updated: 2026-11-05

This document defines the boundary between an independent capture head and a
memory or delivery target. Recon is the first planned Android implementation,
but the protocol is intentionally not Recon-specific: SayIt and future capture
heads can emit the same source envelope, while Quetzal and other compatible
memory systems can receive it.

The protocol freezes source semantics and delivery guarantees. It does not
freeze an account system, transport, storage provider, model vendor, memory
graph, or user interface.

## 1. First principles

### 1.1 Capture is a local commit

A capture succeeds when the original content, its manifest, and the local
outbox record are durably saved. Network access, authorization, destination
selection, transcription, vision processing, and semantic memory processing
must not be prerequisites for capture success.

Airplane mode, remote wilderness, low-signal locations, and deliberate radio
silence are normal operating modes, not error states.

### 1.2 A source is target-neutral

`SourceEnvelope` never contains a Quetzal account, destination account, upload
token, endpoint, or transport choice. A source can be captured before a target
is known and delivered later to one or more compatible destinations.

Target and authorization belong to a separate `DeliveryIntent` created when a
user or a background policy chooses to deliver a pending source.

### 1.3 Originals are authoritative; derivatives are not

The capture head owns the original bytes and their provenance. Transcripts,
OCR, visual descriptions, stitched images, summaries, embeddings, and claims
are derived artifacts. A derivative must identify the source revision and the
processor that produced it; it cannot silently replace the original.

### 1.4 Capture heads do not write semantic memory

A capture head submits sources and precise anchors. It does not write claims,
topics, entities, supports, or conclusions into the memory kernel. The memory
kernel may create those asynchronously after validating the source, version,
authorization, and processor inputs.

### 1.5 Delivery is resumable and idempotent

The same source revision may be retried, resumed, or delivered through another
transport without creating duplicate sources or duplicate blobs. A destination
must reject a different payload submitted under an already accepted source
revision.

## 2. Terminology

| Term | Meaning |
| --- | --- |
| Capture head | A product or device entry point that records raw material, such as Recon or SayIt |
| CaptureSession | A local continuous capture session; it may produce multiple sources |
| Source | A user-committed unit of material, such as one Recon bundle or one SayIt recording |
| SourceAnchor | A stable reference to a source part or precise media location |
| SourceEnvelope | Target-neutral manifest for one source revision |
| Blob | Content-addressed original or derived bytes |
| DerivedArtifact | A generated representation tied to source revisions and processors |
| DeliveryIntent | A later decision to deliver a source to a destination |
| Destination | A memory kernel, import service, file target, or other compatible sink |
| Grant | A scoped, revocable authorization to deliver to a destination |
| Outbox | Durable local records for sources not yet delivered or not fully acknowledged |
| Receipt | A destination response distinguishing accepted source bytes from later processing |
| Job | A durable asynchronous processing or delivery operation |

## 3. Source identity and revisions

### 3.1 IDs

- `sourceId` is a random, globally unique identifier generated by the capture
  head when the source is committed. It is stable across retries and targets.
- A local display identifier such as Recon's `2026-11-05-s-0001` is retained as
  `localId`, but is not globally unique and is not an authority key.
- `captureSessionId` groups sources created during one continuous local
  capture session. It is informational and does not imply that sources must be
  delivered together.
- `partId` is stable within a source and identifies one original or derived
  part.

### 3.2 Revisions

- The first committed source is `revision: 1`.
- A changed original, corrected capture metadata, or user-authored revision
  creates a new revision; it does not mutate an accepted revision.
- The source identity is `(sourceId, revision, manifestHash)`.
- A destination may accept the same identity repeatedly, but must reject a
  different manifest under the same `(sourceId, revision)`.
- A withdrawn revision remains auditable and cannot be silently resurrected by
  an old retry.

## 4. SourceEnvelope v1

The following is the logical wire shape. JSON, CBOR, or another transport
encoding may be used, but the semantics and required fields remain the same.

```json
{
  "protocol": "capture-source/v1",
  "sourceId": "0d5c3e2e-8d5c-4f1c-93b2-2a7b1b0c3a19",
  "revision": 1,
  "manifestHash": "sha256:…",
  "head": {
    "id": "recon",
    "version": "0.1.0",
    "platform": "android"
  },
  "localId": "2026-11-05-s-0001",
  "captureSessionId": "3bdc…",
  "kind": "multimodal_bundle",
  "capturedAt": {
    "startMs": 1790000000000,
    "endMs": 1790000018000
  },
  "captureContext": {
    "timezone": "America/New_York",
    "location": {
      "latitude": 40.0,
      "longitude": -73.0,
      "accuracyM": 18.0,
      "capturedAtMs": 1790000001000
    }
  },
  "parts": [
    {
      "partId": "photo-001",
      "order": 0,
      "modality": "photo",
      "role": "original",
      "capturedAtMs": 1790000001000,
      "rotationDegrees": 90,
      "blob": {
        "contentHash": "sha256:…",
        "mime": "image/jpeg",
        "bytes": 1827364,
        "ref": "blob://sha256/…"
      }
    },
    {
      "partId": "video-002",
      "order": 1,
      "modality": "video",
      "role": "original",
      "durationMs": 8400,
      "blob": {
        "contentHash": "sha256:…",
        "mime": "video/mp4",
        "bytes": 9837462,
        "ref": "blob://sha256/…"
      }
    }
  ],
  "derived": [
    {
      "artifactId": "stitched-preview",
      "role": "stitched_preview",
      "derivedFrom": ["photo-001"],
      "processor": "recon-stitcher@1",
      "blob": {
        "contentHash": "sha256:…",
        "mime": "image/jpeg",
        "bytes": 2345678,
        "ref": "blob://sha256/…"
      }
    }
  ],
  "createdAtMs": 1790000020000
}
```

### 4.1 Required semantics

- `parts` preserves user capture order through `order`; modality-specific file
  names must not be used to reconstruct order.
- `capturedAt` and `createdAtMs` are different: the former describes the
  captured material and the latter describes manifest creation.
- `captureContext` is optional. Location is included only when the user has
  granted it and the head has a valid fix; absence never means “no location”.
- `role: original` is the evidence root. `role: derived` is reserved for
  generated material and must include `derivedFrom` and `processor`.
- Unknown future modalities are preserved as opaque parts by forward-compatible
  receivers; v1 receivers must not silently discard them.

### 4.2 SourceAnchor

An anchor identifies evidence without copying it:

```json
{
  "sourceId": "0d5c3e2e-8d5c-4f1c-93b2-2a7b1b0c3a19",
  "revision": 1,
  "partId": "video-002",
  "locator": {
    "type": "time",
    "startMs": 1200,
    "endMs": 4300
  }
}
```

Supported locator kinds are `whole_part`, `time`, `region`, and `text`. A head
must use `whole_part` when it cannot provide a reliable fine-grained locator;
it must not fabricate precision.

## 5. Local-first lifecycle

The capture transaction is local and target-independent:

```text
capturing
  → staged
  → locally_committed
  → queued
  → waiting_for_network / waiting_for_authorization
  → delivering
  → accepted_by_destination
  → processing
  → ready / partial / failed
```

`locally_committed` means the head has atomically persisted the original files,
the source manifest, and the outbox record. Only this state is required for the
capture UI to report success.

`accepted_by_destination` means the destination has verified the manifest and
accepted the source revision. It does not mean that transcription, vision, or
semantic extraction has completed.

An offline head must:

1. avoid network calls in the capture commit path;
2. show local success after durable local commit;
3. retain the source until the configured local-retention policy permits cleanup;
4. retry delivery with bounded backoff and no duplicate installation;
5. preserve pending work across process death and device restart;
6. expose storage pressure separately from network unavailability.

## 6. DeliveryIntent and authorization

`DeliveryIntent` is created after capture, when the user or a background policy
chooses a destination.

```json
{
  "sourceId": "0d5c3e2e-8d5c-4f1c-93b2-2a7b1b0c3a19",
  "revision": 1,
  "destinationId": "memory-space-uuid",
  "connectorId": "quetzal",
  "grantRef": "keystore://capture-grant/1",
  "createdAtMs": 1790001000000
}
```

The destination is not stored inside the SourceEnvelope. A destination may be
selected days later, and the same source may be delivered to more than one
destination.

### 6.1 One-time authorization exchange

A one-time code or QR/deep link is an activation artifact, not the long-lived
upload credential:

```http
POST /v1/capture/authorization/exchange
```

The exchange returns a target-bound, scope-limited, revocable grant. The grant
should be bound to a Recon device key where practical. Minimum upload scopes:

```text
source:create
blob:write
source:status
source:withdraw
```

It must not grant general memory reads, agent execution, tool calls, or account
administration. Background delivery requires a refreshable grant or an
equivalent revocable long-lived capability; a single-use token cannot support
future automatic uploads after it expires.

The destination derives the authenticated subject and target from the grant.
Recon does not submit an account identifier as an authority claim.

## 7. Logical destination interface

The transport may be HTTPS, a local file exchange, LocalSend, or a future
connector. A compatible destination exposes equivalent operations.

### 7.1 Prepare

```http
POST /v1/capture/sources/prepare
Authorization: Bearer <capture-grant>
Idempotency-Key: <sourceId>:<revision>:<manifestHash>
```

The destination validates the envelope and returns an upload plan containing
the missing content-addressed blobs. Existing blobs must not be re-uploaded.

### 7.2 Upload blobs

```http
PUT /v1/capture/uploads/{uploadSessionId}/{contentHash}
```

Uploads are streamed, resumable where supported, and verified against the
declared content hash. An upload response is not a semantic-memory response.

### 7.3 Commit source

```http
POST /v1/capture/sources/{sourceId}/commit
Authorization: Bearer <capture-grant>
```

The response distinguishes source acceptance from asynchronous work:

```json
{
  "sourceId": "0d5c3e2e-8d5c-4f1c-93b2-2a7b1b0c3a19",
  "revision": 1,
  "state": "accepted",
  "jobs": [
    { "id": "job-1", "kind": "transcribe", "state": "queued" },
    { "id": "job-2", "kind": "vision", "state": "queued" },
    { "id": "job-3", "kind": "extract", "state": "queued" }
  ]
}
```

### 7.4 Status and withdrawal

```http
GET  /v1/capture/sources/{sourceId}
POST /v1/capture/sources/{sourceId}/withdraw
```

Status is source-scoped and revision-aware. Withdrawal invalidates future
processing and derived access according to the destination's lifecycle rules;
it does not pretend to erase media already viewed or copied by an authorized
recipient.

## 8. Recon mapping and implementation plan

Recon already has the correct local-first foundation: the capture screen writes
to an internal staging session, `StagingStore` maintains an order log and
discard marker, `PendingBundle` carries a versioned mixed-media manifest,
`BundleWorker` writes committed files to SAF off the interaction path, and
`WorkScheduler` recovers work through WorkManager. The protocol should extend
that pipeline rather than put network work into capture.

### Phase 0 — freeze the contract

Deliver this document and add protocol fixtures for:

- photo-only, video-only, voice-only, and mixed sources;
- divider-split sessions with shared `captureSessionId`;
- derived stitched output;
- missing optional location;
- unknown future modality;
- duplicate delivery and conflicting same-revision delivery.

No network dependency is required for this phase.

### Phase 1 — durable source manifest

Add a protocol manifest distinct from the transient worker manifest:

- Keep `PendingBundle` v2 as the crash-recovery input to `BundleWorker`.
- Add `CaptureSourceManifest` for the committed bundle and persist it beside
  the SAF bundle or in a durable internal outbox.
- Generate a random `sourceId` at bundle commit; retain Recon's `bundleId` as
  `localId`.
- Map `PendingBundle.orderedItems` to `parts[].order`.
- Record per-part MIME, byte size, duration, rotation, and capture metadata.
- Mark stitched output as `derived` with `derivedFrom` photo part IDs.
- Compute streaming SHA-256 hashes without loading media into memory.

Candidate code locations:

| Current responsibility | Next integration seam |
| --- | --- |
| `pipeline/PendingBundle.kt` | Keep v2; add a separate protocol manifest model |
| `pipeline/ManifestStore.kt` | Add durable source-manifest persistence and migration tests |
| `pipeline/BundleWorker.kt` | Emit the source manifest after SAF copy succeeds |
| `data/storage/BundleFile.kt` / `BundleLibrary.kt` | Enumerate committed parts and preserve subfolder/order metadata |
| `data/storage/StagingStore.kt` | Remain capture-only; do not become the upload queue |

### Phase 2 — local Outbox

Add a local `CaptureOutbox` owned by `AppContainer`, separate from the bundle
save worker:

- persist `(sourceId, revision, manifestPath, localState)`;
- recover pending entries on process start;
- distinguish `waiting_for_network`, `waiting_for_authorization`, and
  `failed`;
- never delete the local source merely because delivery failed;
- add a storage-pressure policy before automatic cleanup.

The local bundle must reach `locally_committed` before the capture UI reports
success. The outbox worker must not run on the camera interaction path.

### Phase 3 — generic delivery seam

Introduce a transport-neutral `SourceDestination` / `DeliveryCoordinator` in
the data layer. Start with a fake destination and a file-export destination so
the retry, idempotency, and status behavior can be tested without Quetzal.

Use WorkManager constraints for delivery (`NetworkType.CONNECTED`, optional
charging / Wi-Fi policy) and keep delivery work separate from `BundleWorker`.

### Phase 4 — LocalSend as a file-transfer connector

Keep the existing LocalSend implementation as a transport connector, not as a
memory authority. Add the protocol manifest to each exported bundle and preserve
the existing relative directory structure. LocalSend remains useful when a
desktop companion or another local importer is the selected destination.

Do not reinterpret a LocalSend receiver's file acceptance as Quetzal memory
acceptance; each destination reports its own receipt.

### Phase 5 — Quetzal connector and deferred authorization

Implement a Quetzal connector after the local protocol is testable:

- exchange a one-time code for a scoped capture grant;
- persist only the grant reference in Android Keystore-backed storage;
- prepare, upload missing blobs, commit, and poll status;
- bind delivery jobs to `(sourceId, revision, destinationId)`;
- refresh or pause when authorization expires;
- support manual target selection without changing SourceEnvelope.

Recon must not depend on Quetzal account data, Claim schemas, or Quetzal's
internal memory RPCs.

### Phase 6 — user-visible delivery state

Only after the background protocol is reliable should Bundle Preview show
delivery state. The minimum UI should distinguish:

- saved locally;
- waiting for network;
- waiting for authorization;
- delivered to target;
- target processing;
- delivery failed with retry.

The first capture success surface must remain local and immediate.

## 9. Compatibility and security requirements

- Protocol versions are negotiated explicitly; unknown required fields fail
  closed, while unknown optional fields are preserved when possible.
- Account and target authority come from the authenticated grant, not from
  model output or user-editable JSON.
- Grants are scoped, revocable, expiring, and never written into a source
  manifest or ordinary logs.
- Raw media is streamed and never loaded wholesale merely to upload it.
- Source, revision, manifest hash, and blob hashes are retained for audit and
  retry; vector indexes and semantic projections remain rebuildable.
- A connector failure must not erase a locally committed source.
- A memory kernel may report `accepted` before semantic processing and must not
  claim `ready` until its own processing contract is satisfied.

## 10. Non-goals for v1

- No requirement that Recon, SayIt, or another head have a user account at
  capture time.
- No requirement that a source be delivered to exactly one destination.
- No direct sharing of Quetzal Claim or Topic schemas with capture heads.
- No mandatory local transcription, OCR, vision model, or semantic model.
- No promise that withdrawal can erase information an authorized recipient has
  already viewed or copied.
